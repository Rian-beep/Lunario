# Full-mission search

`searchMissionWindows(catalog, manifest, request, options)` evaluates each entire stay through `evaluateScenario`. Every candidate starts from a deep clone of the base vehicle, initial state of charge, requirements, operations and reports. Only location and start/end change. The current custom point remains attached to its own base site ID; another selected ID means that catalog site.

The request uses 1–20 distinct site IDs, inclusive first/last candidate-start indices, positive duration/cadence in samples, and 1–100 retained results. More than 10,000 site/start combinations is rejected with narrowing instructions. A final epoch is not another forcing interval. A stay outside the catalogue endpoint or evidence manifest is counted as outside and never shortened. Schedules longer than the requested mission are rejected before numerical evaluation.

`planningSearchKey` includes complete base inputs, normalized custom longitude, sorted site IDs, every search control, catalogue metadata and the evidence manifest. The UI must abort its previous AbortController when starting a replacement search, compare the current key before publishing, and may supply `isCurrent(key)` for engine-side rejection. An aborted or superseded search rejects with AbortError and returns no final rows. Independent callers do not cancel one another through global mutable state.

The cooperative budget is 8 ms between indivisible synchronous assessments, followed by a timer yield compatible with file URLs. It cannot interrupt one numerical assessment. Progress includes requestKey, completed, total and copied outcome counts. The 1,000-start synthetic test verifies timers run before completion; this is a scheduling assertion, not a device performance guarantee.

Rows sort by assessed passes, conditional, incomplete, failures, not configured; reserve margin descending, geometric outage ascending, arrival ascending, site ID ascending. No weighted score combines incompatible units. All outcomes are counted; returned rows are capped at maxResults and `truncated` explicitly reports omitted assessed rows. Increase the cap or narrow the range to inspect omitted cases. A single-site 31-start daily calendar fits the maximum 100 rows without truncation. Opening any retained row supplies its exact state and reproduces its assessment.

`evaluateAlternative` retains its existing arguments and accepts an optional seventh evidence manifest. Its default is the bundled, validated static manifest (no runtime fetch); synthetic callers supply their own explicit manifest. Matrix criteria populate `requirements.extraScreens`; an explicit positive permitted unmet-energy allowance disables requireZeroUnmetWh, while the independent reserve requirement remains enabled as configured. New nested state is deep-cloned. Status maps full assessment outcomes: pass→meets, fail→fails, incomplete/not-configured→unknown, conditional→conditional; outside remains outside. `assessment` is attached to every evaluated cell. Metrics and deltas use that shared evaluator's timeline and aggregates, with no second power model or independent constraint rules.

Automated checks: `node --import tsx --test tests/planning-search.test.ts tests/alternatives.test.ts`. Search fixtures cover full-stay storage versus sunlight means, independent initial state, observer contact mask, unavailable/partial evidence, exact reproduction, boundary rejection, keys, abort/stale results, deterministic ordering, caps and cooperative yielding. Integrator owns UI status mapping, browser interaction and updated T05/T06 authority regression checks.
