# Lunario audience task sheet — ready to run, no participants enrolled

This protocol has **not** been run with people. Agent actions and DOM/emulation evidence in REPORT.md are separate. Do not fill participant fields from automated results or infer learning, engagement, screen-reader usability or mission qualification from task completion.

Use a facilitator and one participant on the participant’s normal device. Allow about 25–35 minutes, stopping sooner if the participant wishes. Start with fresh app storage in a disposable browser profile, no saved scenario and no observer explanation of the result. Use the parent’s exact candidate; record its URL, commit, build-receipt hash, offline HTML hash (if used), model and dataset. Record internet/offline state, browser/OS, device, viewport, zoom, input method, theme and assistive technology. Obtain consent under the study owner’s actual process. Use anonymous codes and task notes; avoid names, contact details or unsolicited recordings.

Assign an audience task set that matches the participant’s experience. Rotate light/dark starting order across sessions; record which was used rather than pooling as equivalent. Run first-load observations before any practice. Do not switch to a pre-warmed profile to improve timings. Record loader visibility separately from first usable map and first usable lander; long reverse-tunnel transfers are not device performance measurements.

## Neutral task prompts

| Audience | Prompt to read verbatim | Observe without coaching | Completion evidence |
| --- | --- | --- | --- |
| Public P1 | “Choose a south-pole location that interests you. Tell me where you are and what the map says about it.” | Can they find site selection, distinguish candidate coordinates from a historical landing and keep the selected name in view? | Selected site/coordinates; participant’s own description; any wrong-site selection or help. |
| Public P2 | “Find the landing experiment, watch it, and explain the result. Change one setting you think matters, then try it again.” | Route taken, any empty/loading state, play/pause and retry discovery; do they confuse prediction, touchdown and accepted limits? | Baseline and edited input, observed play/retry, displayed outcome before/after, participant explanation. No score for physical landing qualification. |
| Public P3 | “Does seeing Earth here mean the spacecraft can communicate? Show me why.” | Can they find the scope note and separate geometry, link hardware and booked service? | Relevant displayed evidence plus verbatim explanation, scored after answering. |
| Educator E1 | “Pick a site and stay. Ask a question about changing just the array height. Predict what will change before revealing any result.” | Site/date discoverability, prediction before reveal, baseline capture, independent array/antenna concepts. | Exact site/date and captured baseline, timestamped prediction, single changed field. |
| Educator E2 | “Run your experiment. Explain what changed and what did not, using the equation and the results.” | Can they interpret native equation symbols/units, full-stay table, terrain/sphere and unknowns? | Actual held/changed inputs, table values and unit-aware explanation. Score against this captured computation, not a universal ‘higher is better’ claim. |
| Educator E3 | “Save the investigation and prepare a student handout and a teacher copy that you could use later.” | Save conclusion, distinguish worksheet/notebook/material builder, locate downloaded files. | Separate student and teacher exports open successfully; student sheet does not expose teacher answers; exact scenario/model retained. |
| Planner L1 | “Keep the hardware and stay length fixed. Assume arrival slips by a day. Find a candidate and explain the first problem it faces.” | Reference/candidate identity, held hardware/requirements, arrival shift, first-failure inspection. | Before/after scenario diff contains date shift only; failure context and scope described. |
| Planner L2 | “Compare a small set of alternative arrivals. Choose one to inspect and say what this search does and does not establish.” | Explicit tested grid, finite ranking, terrain/sphere, unknown and stale external evidence. | Tested dates/sites recorded, candidate and reason; no inferred global optimum or landing readiness. |
| Planner L3 | “Save that case, export it, then reopen the saved file and check that you recovered the same case.” | Save vs open candidate vs export discoverability; import feedback and recomputation. | Export/import exact scenario diff, model/dataset and reassessment result; any stale or missing evidence remains visible. |

Ask after each task: “What made that difficult?” and “What do you think this result means?” Record time, wrong turns, errors, requests for help and whether the task was completed unassisted, completed with help, abandoned or blocked. If assistance is given, write its exact wording and when. Do not turn observer scoring guidance into task hints.

For selected participants, repeat the controls they just used at **native browser 200% zoom**, checking the browser zoom indicator and layout width; device scale or pinch zoom is a different condition. On a real touch device repeat site selection, modal dismissal and chart sample inspection. Record keyboard-only travel separately: visible focus, Space/arrow behavior, dialog Tab/Shift+Tab, Escape and opener restoration. For screen-reader sessions record the actual screen reader/version, reading order and spoken names/values; an accessibility tree or `aria-live` attribute alone is insufficient.

## Scoring and export

Keep action completion and explanation correctness separate. Score explanation as correct / partly correct / incorrect / not assessable, with a quoted answer and a reason tied to the displayed scenario. Freeze scoring after the answer. Confidence ratings (optional 1–5 before/after) are self-report, not measured learning. Do not interpret completion latency as engagement or generalize from a convenience sample.

Use OBSERVATION-TEMPLATE.csv for one row per task. Use SESSION-TEMPLATE.json for artifact/environment and session metadata. Leave fields blank when unknown; use no invented times, participants or success counts. If using Lunario’s “Try the tasks with an audience”, explicitly select **Observed human participant**, **Agent walkthrough** or **Self-reported experience** as applicable and export the study evidence. The app’s recorder-supplied label is not independent verification. Keep the original exported JSON, file hash and facilitator notes together under the study owner’s approved storage policy. Redact identifying data before repository handoff.

Study-owner follow-up: recruit actual intended audiences, arrange real mobile and assistive-technology sessions, independently review disputed explanations, and report sample/recruitment limitations and every blocked/abandoned task. No human acceptance claim is warranted until that evidence exists.
